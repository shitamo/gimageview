10. Tips

Making drawing in the image view faster

Check [Preferences | Image Window | Image | Keep the original image in memory]. For the image windows open only, [File | Memory Buffer] (Ctrl + B) turns it on and off.

When an image has been shown, GImageView drops the original image (the pixels read). So when the zoom is changed or the image is rotated or flipped, the original image is read from the file again. Kept in memory, it is not read again, which is faster the larger the image is.

When an image is opened first, it is read from the file whatever the setting, so this option does not matter there. Keeping the original image uses width × height × 3 or 4 bytes of memory more per image (about 40 MB for a photo of 12 megapixels). For this reason the default setting is OFF. Animations, movies and audio are kept whatever the setting.

Changing the thumbnail size temporarily

Change the thumbnail size in the toolbar (press Enter when typing a number), then use [Edit | Reload Cache] (Shift + R) or [Edit | Update All Thumbnails] (Ctrl + R) to apply it.

If you use "Reload Cache", the cached images are enlarged (or reduced) to the new thumbnail size and displayed. Reducing is fine, but when enlarging, the dots become coarse. To avoid this, use "Update All Thumbnails". The cache is recreated at the new size, so the dots do not become coarse.

The thumbnail size belongs to each tab: switching tabs shows the size of that tab. A new window or an empty tab goes back to [Preferences | Thumbnail Window | Thumbnail View | Thumbnail Size]. With "Save window state on exit" in [Preferences | Thumbnail Window] on (the default), the value in the toolbar at exit is saved there and is the size from then on.

Differences between [Refresh List], [Reload Cache] and [Update All Thumbnails]
Refresh List (Shift + Ctrl + R)

Updates only the differences between the information on disk and in memory. It only updates the file list and does not resize the thumbnails.

Reload Cache (Shift + R)

Discards all information and reads all information from disk again. At this time, if a cache exists it is read from the cache, and if not, the thumbnail is created from the original image. If a cache exists, only the thumbnail is resized.

Because it is a resize and not a re-creation, if the saved cache is smaller than the specified size, the thumbnail is simply enlarged and the image looks bad.

Update All Thumbnails (Ctrl + R)

Discards all information and reads all information from disk again. All thumbnails are re-created from the original images. When the displayed thumbnail size has been changed, this is probably the best one to use. The part on screen is made first and the rest in the background, keeping the scroll position. The progress (n/N) is shown while it runs, and the stop button in the toolbar stops it.

About custom layouts

[View | Layout] places the views of the thumbnail window (directory view, thumbnail view, preview) as Layout 0 to 4 (Ctrl + 0 to 4). Layout 0 is the default. These layouts are fixed and cannot be changed.

For other arrangements there is "Custom". The layout becomes "Custom" by itself with these:

  • [View | Layout | Window Composition] chooses how the window is split (the panes horizontal or vertical, and how they are put together).

  • Dragging a view and dropping it on another one swaps the two. The parts to drag are the tabs of the thumbnail view, the toolbar of the directory view and the tabs of the preview (Preview, Data, Note).

The custom layout is saved as these six items of ~/.gimv/gimvrc, which can also be edited by hand while gimv is not running:

  • thumbwin_pane1_horizontal (whether pane1 is split horizontally or vertically)

  • thumbwin_pane2_horizontal (the same for pane2)

  • thumbwin_pane2_attach_1 (whether pane2 is attached to child1 or child2 of pane1)

  • thumbwin_widget[0] (the widget attached to the other side of pane1: 1 is the directory view, 2 the thumbnails, 3 the preview)

  • thumbwin_widget[1] (child1 of pane2)

  • thumbwin_widget[2] (child2 of pane2)

Layouts 0 to 4 are these six values set in advance.

How duplicates are found

[Tools | Find Duplicates...] goes through the images of the active tab in the steps below and sorts what it finds into three kinds of groups: Identical, Other Sizes and Similar. It searches in another thread: the window can be used meanwhile.

  1. The same files: the md5 is computed only for the files of the same size (in bytes); the same md5 means the same bytes. A file whose size no other has is not read.

  2. The pictures read small: one of each set of the same files is read small (about 128 dots), turned as its EXIF orientation says, squeezed into a 32x32 frame whatever its shape, and the R/G/B means of each part are taken (some programs call it a "fingerprint"). The thumbnails are not used: the images the thumbnail view has not loaded yet are compared too.

  3. The pictures compared: the R/G/B differences of two fingerprints are averaged (0 to 1.0); 1.0 minus that is how alike they are. At or above the value of the preferences they match. Images whose total brightness is too far apart cannot match and are not compared.

  4. The kinds: a group of the same files only is Identical. When the images that match all have the same shape and no two of them have the same size, it is Other Sizes (copies included); else Similar. Images of the same size but other bytes (saved again, edited) are Similar.

How alike they must be is "Accuracy" in [Preferences | Search] (0.97 by default: 97% or more alike match). A lower value puts more images in Similar.

In the Identical and Other Sizes groups the one with the most pixels (then the largest file, the oldest, the shortest path) is marked Keep and the others Delete. In an Other Sizes group, an image twice as large or more is checked for being a smaller one only made larger: then it shows "Looks like an enlarged copy" and is not the one kept (see "How an enlarged copy is told" below). The Similar groups may be other shots: all are marked Keep. Which to keep is for a person to check and decide. "Move to Trash..." moves those to delete of the group shown, "Move All Marked to Trash..." those of all the groups at once; they are compared with the image kept again first.

Because of how it works, it may not do what one expects in these cases.

  1. Images whose color balance or brightness has changed as a whole match less (every part differs evenly).

  2. Images with a part (top/bottom/right/left) cut off match less (parts that do not correspond are compared). Rotated or mirrored images do not match.

  3. A copy only blown up is not told when it is less than twice as large, when the picture has little detail, or when it is a JPEG saved at a low quality (about 70 or less): it has more pixels and is marked Keep. One blown up by AI (waifu2x, ...) has detail made up and may not be told.

  4. Images gimv shows but gdk-pixbuf cannot read are looked at for Identical only. The images in archives are not compared.

How an enlarged copy is told: an ordinary enlarging (nearest, bilinear, bicubic, Lanczos, of any program) makes each pixel of the large image a weighted sum of the pixels around its place in the small one. The best weights to predict the large image from the small one are fitted on half of the pixels, and the error of the prediction is measured on the other half: an enlarged copy is predicted down to about its JPEG noise, a picture really larger keeps the detail the small one does not have. The error is compared with the error of predicting the small image from itself made smaller by as much (photographs have alike detail at all scales: about the same for a real one, less than 0.35 times for an enlarged copy). With the test pictures, about nine in ten of the copies enlarged twice were told, and no real one was taken for a copy; it takes about 0.2 seconds a pair (12 million pixels).

To find the same files across folders, not only in the active tab, use [Tools | Find Duplicates in the Index...] (the index looks for them in the background): see "Find Duplicates in the Index...".
